# Dress V. Сервер ИИ-примерки

HTTP-сервис принимает снимок посетителя и референсы из подготовленной карточки WooCommerce, хранит задание в памяти и отдаёт результат исходной сессии. Тестовый режим возвращает синтетический PNG и использует заглушку визуальной проверки. Адаптер OpenAI Images Edits проверяется отдельно через имитацию транспорта.

**Статус на 20 ноября 2026 года.** HTTP API и закрытый HTTPS-канал из рабочего WordPress на Hermes развёрнуты и проверены синтетической загрузкой через Apache/PHP. Действующая служба работает в тестовом режиме. Клиентская кнопка, плагин и реальная генерация пока не подключены.

## Переключение генерации на Hermes

WordPress использует прежний HTTP API Dress V. Служба выбирает генератор по `DRESSV_PROVIDER` при запуске. Значение `mock` возвращает синтетическую картинку. Значение `image-edits` использует один транспорт с настраиваемым HTTPS endpoint и Bearer-ключом. [Настройка переключателя](OPENAI-SETUP.md)

## Локальный прогон

Нужен Python 3.10 для версии Pillow из `requirements.txt`. Тесты поднимают HTTP на loopback и используют только синтетические изображения.

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src python -m unittest discover -s tests -v
```

Для ручной проверки используется `PYTHONPATH=src python -m dressv --mock`. В каталоге `CREDENTIALS_DIRECTORY` должен быть файл `wordpress-token` с отдельным тестовым токеном. Слушатель стартует на `127.0.0.1:18444`. Пример конфигурации systemd приведён в `deploy/dressv-mock.service`.

## HTTP-контракт

Все вызовы передают `Authorization: Bearer <межсерверный токен>` и `X-DressV-Session: <непрозрачный идентификатор>`. Будущий плагин WordPress вычисляет идентификатор из текущей серверной сессии. Токен, идентификатор сессии и ключ идемпотентности используют 16–128 символов ASCII из `A–Z a–z 0–9 _ -`.

- `POST /v1/jobs` принимает `Idempotency-Key` и multipart с полями `metadata`, `portrait` и 1–4 полями `reference` в порядке референсов. В метаданных передаются `schema_version: 1`, строковые `product_id` и `prompt`, массив строк `required_details`. Допустимы PNG, JPEG и WebP до 16 МиБ в сумме, до 4096 пикселей по стороне и до 12 Мп на снимок. Новое задание возвращает `202` и `job_id`. Повтор возвращает `200` с тем же ID, изменение данных с тем же ключом даёт `409`.
- `GET /v1/jobs/{id}` возвращает `queued`, `running`, `ready` или `failed`. Для ошибки добавляется безопасный код `provider_failed` или `quality_rejected`.
- `GET /v1/jobs/{id}/result` отдаёт готовый PNG с `Cache-Control: no-store`. До готовности возвращает `409`. Истёкшее, удалённое или чужое задание возвращает `404`.
- `DELETE /v1/jobs/{id}` подтверждает выдачу или отменяет задание. Повтор возвращает `204`. Ключ идемпотентности хранится до исходного TTL, поэтому повтор запроса после удаления в этом окне не создаёт новое задание. По умолчанию TTL равен десяти минутам.

Сервис держит в процессе до шести заданий, из которых до двух выполняются одновременно. Результат ограничен 8 МиБ. Таймер очищает просроченные задания без входящих запросов. Перезапуск процесса очищает состояния и данные в памяти.
